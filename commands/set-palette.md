# /set-palette — commit the project to a palette

`/set-palette` is the explicit lock mechanism. Once a project decides "this is the palette," `/set-palette` writes `memory/PALETTE.json` and every downstream `/magic` run reads it as ground truth — CONTEXT must build palette_strategy on top of it, BUILD must use the exact OKLCH values, and AUDIT fails the gate if drift is detected.

This is the inverse of `/houdini`'s exploration mode. Houdini rotates families to find a direction; `/set-palette` ends the rotation.

## Pre-run setup

Capture `$PROJECT_ROOT` via `pwd` and `mkdir -p "$PROJECT_ROOT/memory"`. The lock file lives at `$PROJECT_ROOT/memory/PALETTE.json`.

## Three invocation forms

### Form A — commit to a family

```
/set-palette <family-key>
```

Family keys: `industrial-mono`, `warm-editorial`, `electric-acid`, `deep-jewel`, `washed-pastel`, `dichromatic-print`, `oxidized-metal`, `phosphor-terminal`.

Behavior:

1. Validate `<family-key>` against the list above. If unknown, list the valid keys via stdout and stop.
2. If `memory/PALETTE.json` already exists, Read it and warn the user via AskUserQuestion: "A palette lock for family <existing-key> already exists. Replace it with <new-key>?" Options: "Replace", "Cancel". On cancel, exit silently.
3. If `seeds/tokens.css` exists, Read it and lift any `--ink`, `--paper`, `--accent`, `--accent-2`, `--mute`, `--line` (or similar role-named) OKLCH custom properties out of the `:root` block. If you find tokens, use them. If you do not, derive a sensible token set from the family's exemplar OKLCH values (see `workflows/houdini.js` PALETTE_FAMILIES constant for the per-family examples) and document in the lock's `source` field that the tokens are derived, not extracted.
4. Write `memory/PALETTE.json` with this exact shape:
   ```json
   {
     "family": "<family-key>",
     "tokens": {
       "ink": "oklch(...)",
       "paper": "oklch(...)",
       "accent": "oklch(...)"
       // additional roles as found / derived
     },
     "locked_at": "<ISO 8601 UTC timestamp from `date -u +%Y-%m-%dT%H:%M:%SZ`>",
     "source": "set-palette | seeds/tokens.css" OR "set-palette | family-default",
     "notes": "<one-line description of why locked, if the user provided one; else empty string>"
   }
   ```
5. Echo to the user: `palette locked → family=<key>, tokens=<N>, source=<source>. /magic runs will honour this lock; pass --palette none to bypass for a single run.`

### Form B — clear the lock

```
/set-palette none
```

Behavior:

1. If `memory/PALETTE.json` does not exist, echo `no palette lock to clear; project is already in explore mode.` and stop.
2. If present, Read it to capture the family that was locked (for the confirmation message). Delete the file via Bash: `rm "$PROJECT_ROOT/memory/PALETTE.json"`.
3. Echo: `palette unlocked (was family=<old-key>). /houdini will rotate; /magic will infer palette per-run.`
4. The `recent-palettes.json` anti-list is left in place — it represents project history and is useful for the next exploration round.

### Form C — pull from the current seed

```
/set-palette from-seed
```

Behavior:

1. Require `seeds/tokens.css` AND `memory/DESIGN_APPROACH.md` to both exist. If either is missing, echo: `set-palette from-seed requires a completed /houdini run (need seeds/tokens.css + memory/DESIGN_APPROACH.md). Run /houdini first, then re-invoke.` and stop.
2. Read `memory/DESIGN_APPROACH.md` and grep for the `## Palette family —` line. Capture the family-key from that line. If the design approach was generated by an older houdini that did not write the family line, ask the user via AskUserQuestion which family to lock to — list all eight options.
3. Read `seeds/tokens.css`. Extract every `--<role>: <value>;` declaration from the `:root` block where `<value>` is an `oklch(...)` literal. Build the `tokens` object from those.
4. Write `memory/PALETTE.json` as in Form A (warn-then-replace if a prior lock exists), with `source: "set-palette | from-seed (run_slug=<latest>)"`.
5. Echo: `palette locked from latest seed → family=<key>, tokens=<N>. /magic runs will honour this lock.`

### Form D — inline custom palette

```
/set-palette custom "ink:oklch(20% 0.04 280),paper:oklch(96% 0.01 80),accent:oklch(64% 0.22 145)"
```

For projects whose palette doesn't fit any of the eight named families — brand-supplied, hand-tuned, lifted from a competitor, anything specific. Two forms accepted:

- Role-labeled: `"role:oklch(...),role:oklch(...),..."` — each token has an explicit role name. Roles may be anything (`ink`, `paper`, `accent`, `accent-2`, `brand-primary`, `foreground-muted`, etc.).
- Bare positional: `"oklch(...),oklch(...),oklch(...)"` — assigned to roles `ink, paper, accent, accent-2, mute, line` in order. Max 6.

Behavior:

1. Parse the inline string. Use the same parser shape as the workflow's `parsePaletteArg` (split on top-level commas — preserve `oklch(...)` parens — then split each part on `:` for the role:value form, or assign positionally for bare OKLCH values). Every value MUST be an `oklch(...)` literal; reject hex/rgb with a clear error.
2. If `memory/PALETTE.json` already exists, warn-then-replace via AskUserQuestion as in Form A.
3. Write `memory/PALETTE.json` with `family: "custom"` and the parsed tokens object, `source: "set-palette | inline custom"`, optional `notes` if the user supplied one as a trailing flag like `--notes "brand-supplied 2026 refresh"`.
4. Echo: `palette locked → family=custom, tokens=<N> (<role list>), source=inline. /magic runs will honour this lock.`

### Form E — describe it in plain English

```
/set-palette prose "warm coral with complementing tones that evoke warmth"
/set-palette prose "muted forest green with cream and one rust accent"
/set-palette prose "Le Labo apothecary — cream paper, espresso ink, one olive accent"
/set-palette prose "the colors of a Hayao Miyazaki sunset over Tokyo"
```

For users who do not want to think in OKLCH. The command runs the same translator agent that the workflow uses for `--palette "<prose>"`, then writes the result to `memory/PALETTE.json`.

Behavior:

1. Capture the prose (everything after the `prose` token, with surrounding quotes stripped). Require at least 6 characters and 4 word characters — shorter inputs error with the message `prose too short; describe in a sentence or two`.
2. If `seeds/tokens.css` and `memory/DESIGN_APPROACH.md` exist, Read them so the translator has the same context the workflow gives it. If not, the translator works from the prose alone.
3. Invoke the translator agent inline (in the command body, via Agent tool with subagent_type=general-purpose). Prompt: "Translate this natural-language palette description into 3-6 OKLCH tokens. Roles: ink, paper, accent, accent-2 (optional), mute (optional), line (optional). Every value must be an `oklch(...)` literal. Enforce impeccable bans: no AI-purple (~280 hue indigo-violet), no beige+brass, no pure black-on-white. Return JSON: `{ tokens: { role: \"oklch(...)\", ... }, interpretation: \"<one sentence>\" }`." Pass the prose + any read context as additional input.
4. If the translator returns ≥ 2 valid OKLCH tokens, proceed. If not, retry once with a shorter, more constrained prompt. If still no usable tokens, error: `translator could not derive tokens from "<prose>". Try a more concrete description (name the dominant hue, the ink, and at least one accent).`
5. If `memory/PALETTE.json` already exists, warn-then-replace via AskUserQuestion as in Form A.
6. Write `memory/PALETTE.json` with `family: "custom"`, the parsed tokens object, `source: "set-palette | prose"`, plus a `notes` field containing the original prose AND the translator's interpretation so the lock file carries the audit trail:
   ```json
   {
     "family": "custom",
     "tokens": { ... },
     "locked_at": "<iso>",
     "source": "set-palette | prose",
     "notes": "prose: \"<original>\"\ninterpretation: \"<translator one-liner>\""
   }
   ```
7. Echo: `palette locked from prose → family=custom, tokens=<N>. Interpretation: <translator one-liner>. /magic runs will honour this lock.`

### Form F — load from a file

```
/set-palette --from <path>
/set-palette --from ./brand/tokens.css
/set-palette --from ./palette.json
```

For palettes that live in a file the user already maintains (a brand tokens stylesheet, a design-system export, etc.).

Behavior:

1. Resolve `<path>` against `$PROJECT_ROOT`. Reject paths outside the project (no `../` escapes, no absolute paths outside `$PROJECT_ROOT`) with an error.
2. Read the file. Branch on extension:
   - `.css` / `.scss` — extract every `--<role>: oklch(...);` declaration from the FIRST `:root { ... }` block. If multiple `:root` blocks exist, merge in source order; later wins on conflict.
   - `.json` — parse as JSON. Accept two shapes: `{ "tokens": { "role": "oklch(...)", ... } }` (preferred) or a flat object `{ "role": "oklch(...)", ... }` whose values are all OKLCH strings.
   - Other — error: "set-palette --from only supports .css, .scss, and .json files."
3. If zero OKLCH tokens parsed, error with the path and a hint about the expected shape; do not write.
4. If `memory/PALETTE.json` already exists, warn-then-replace via AskUserQuestion as in Form A.
5. Write `memory/PALETTE.json` with `family: "custom"`, the parsed tokens object, `source: "set-palette | --from <path>"`. The `family` field is `"custom"` even though the file may have come from a known design system — the workflow only treats one of the eight family keys as having a canonical brief; everything else is custom.
6. Echo: `palette locked from <path> → family=custom, tokens=<N>. /magic runs will honour this lock.`

## After the lock

- Every subsequent `/magic <intent>` reads `memory/PALETTE.json` during CONTEXT and treats its tokens as ground truth. The agent will NOT re-derive a palette from the brief — it composes ramps and contrast targets on top of the locked anchors.
- `/magic`'s AUDIT preflight gains a drift check: if any HTML or CSS file in the build redefines a locked role with a different OKLCH value (>0.5% L/C or >2° H), the gate fails with `block` severity. Hex/rgb literals where the palette would suffice are flagged as `warn`.
- `/houdini --palette none` and `/magic --palette none` temporarily bypass the lock for a single run without modifying the file.
- `/palette-status` shows the current state at any time.

## When NOT to use this

- During exploration / cold-start. Locking too early defeats the variance that houdini is designed to surface. Run `/houdini` 2-3 times across different angles first, find the direction you want, THEN lock.
- For tweaking individual token values. Once locked, you edit `memory/PALETTE.json` directly — there is no `/set-palette --tweak <role> <value>` form. The file is plain JSON; edit it.
- For experimenting with one-off looks. Use `/magic --palette <other-family>` to ride the lock; the override is per-run and the lock survives.

## Anti-patterns

- Locking before you have a design direction. The lock is a commitment, not an exploration tool.
- Locking and then ignoring drift findings in AUDIT. If the gate fails on drift, fix the tokens — do not paper over it.
- Manually deleting `memory/PALETTE.json` outside this command. The file is fine to delete by hand, but doing so silently leaves the `source` and `locked_at` audit trail behind in `recent-palettes.json` and downstream tools won't notice the change until next run.
